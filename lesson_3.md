#### Шпаргалка команд по третьему уроку

<details>
<summary>Перенос коммитов из ветки в ветку</summary>

✅ Применяет изменения из одного конкретного коммита (из любой ветки) в текущую ветку.
Полезно, чтобы «перенести» нужный фикс или функцию без слияния всей ветки:

```sh
git cherry-pick <hash-commit>
```

✅ Применяет диапазон коммитов от X (исключая) до Z (включая).
Требует указания коммитов в правильном порядке (обычно X — старый, Z — новый):

```sh
git cherry-pick X..Z
```

</details>

<details>
<summary>Слияние веток merge</summary>

✅ Сливает (merge) ветку <branch-name> в текущую активную ветку. Если нет конфликтов и в основной ветке не было новых коммитов — может произойти fast-forward:

```sh
git merge <branch-name>
```

✅ Принудительно создаёт merge-коммит, даже если возможно fast-forward. Полезно для сохранения чёткой истории ветвления:

```sh
git merge --no-ff <branch-name>
```

✅ Отменяет начатое слияние до завершения (до git commit). Восстанавливает рабочую директорию и индекс в исходное состояние:

```sh
git merge --abort
```

</details>
<details>
<summary>Перебазирование веток rebase</summary>
✅ Перемещает коммиты текущей ветки поверх указанной ветки (например, main).
Создаёт линейную историю, но переписывает историю — не для публичных веток!

```sh
git rebase <branch>
```

✅ Продолжает операцию rebase после разрешения конфликта и добавления файлов через git add.

```sh
git rebase --continue
```

✅ Пропускает текущий конфликтный коммит при rebase и переходит к следующему.

```sh
git rebase --skip
```

✅ Полностью отменяет операцию rebase и возвращает репозиторий в состояние до её начала.

```sh
git rebase --abort
```

✅ Запускает интерактивный режим: позволяет редактировать, объединять, удалять, переупорядочивать коммиты.

```sh
git rebase -i <branch_name>
# или
git rebase -interactive <branch_name>
```

</details>
<details>
<summary>Когда использовать rebase, а когда merge</summary>

🧩 Используй merge, когда:
✅ Работаешь в команде над общей веткой (например, main, develop или feature/team-task).
→ merge сохраняет всю историю: кто, когда и что делал. Это честно и безопасно.
✅ Ветка уже опубликована на GitHub/GitLab (то есть другие могут её видеть или использовать).
→ rebase может «переписать историю» и запутать других — это как менять страницы в чужой книжке!
✅ Хочешь чётко видеть, когда и какие ветки объединялись.
→ Например, удобно видеть: «Ага, фича X влилась 5 апреля».

🧹 Используй rebase, когда:
✅ Ты работаешь один в своей личной ветке и хочешь «причесать» историю перед тем, как отправить её в общую ветку.
→ Например, у тебя 10 мелких коммитов вроде «fix», «try again», «oops» — ты можешь их объединить и поставить аккуратно поверх main.
✅ Хочешь чистую, линейную историю без «мусора».
→ После rebase лог выглядит как прямая дорожка: коммит → коммит → коммит. Легче читать!
✅ Готовишь pull request и хочешь, чтобы твои изменения выглядели так, будто ты писал код после последнего обновления основной ветки.

</details>
<details>
<summary>Разрешение конфликтов через командную строку</summary>
✅ Показывает различия между версиями файлов. Во время конфликта — помогает увидеть детали расхождений.

```sh
git diff
```

✅ Проверяет, остались ли в файлах маркеры конфликтов (<<<<<<<, =======, >>>>>>>).
Если есть — выводит их; если нет — ничего не выводит.

```sh
git diff --check
```

✅ Берёт «их» (входящие) версию файла (из сливаемой ветки) при разрешении конфликта.

```sh
git checkout --theirs <file>
```

✅ Берёт «наши» (уже имеющиеся) версию файла (из сливаемой ветки) при разрешении конфликта.

```sh
git checkout --ours <file>
```

</details>

<details>
<summary>Отправка веток на удаленный репозиторий</summary>

✅ Отправляет указанную ветку на удалённый репозиторий (устанавливаем с ней связь).

```sh
git push -u origin <branch_name>
```

✅ Отправляет все локальные ветки на удалённый репозиторий.

```sh
git push --all origin
```

✅ Показывает связь между локальными и удалёнными ветками,

```sh
git branch -vv
```

</details>
